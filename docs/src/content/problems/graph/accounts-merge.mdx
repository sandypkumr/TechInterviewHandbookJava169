Given a list of `accounts` where each element `accounts[i]` is a list of strings, where the first element `accounts[i][0]` is a name, and the rest of the elements are **emails** representing emails of the account.

Now, we would like to merge these accounts. Two accounts definitely belong to the same person if there is some common email to both accounts. Note that even if two accounts have the same name, they may belong to different people as people could have the same name. A person can have any number of accounts initially, but all of their accounts definitely have the same name.

After merging the accounts, return the accounts in the following format: the first element of each account is the name, and the rest of the elements are emails **in sorted order**. The accounts themselves can be returned in **any order**.

**Example 1:**

```
Input: accounts = [["John","johnsmith@mail.com","john_newyork@mail.com"],["John","johnsmith@mail.com","john00@mail.com"],["Mary","mary@mail.com"],["John","johnnybravo@mail.com"]]
Output: [["John","john00@mail.com","john_newyork@mail.com","johnsmith@mail.com"],["Mary","mary@mail.com"],["John","johnnybravo@mail.com"]]
Explanation:
The first and second John's are the same person as they have the common email "johnsmith@mail.com".
The third John and Mary are different people as none of their email addresses are used by other accounts.
We could return these lists in any order, for example the answer [['Mary', 'mary@mail.com'], ['John', 'johnnybravo@mail.com'],
['John', 'john00@mail.com', 'john_newyork@mail.com', 'johnsmith@mail.com']] would still be accepted.
```

**Example 2:**

```
Input: accounts = [["Gabe","Gabe0@m.co","Gabe3@m.co","Gabe1@m.co"],["Kevin","Kevin3@m.co","Kevin5@m.co","Kevin0@m.co"],["Ethan","Ethan5@m.co","Ethan4@m.co","Ethan0@m.co"],["Hanzo","Hanzo3@m.co","Hanzo1@m.co","Hanzo0@m.co"],["Fern","Fern5@m.co","Fern1@m.co","Fern0@m.co"]]
Output: [["Ethan","Ethan0@m.co","Ethan4@m.co","Ethan5@m.co"],["Gabe","Gabe0@m.co","Gabe1@m.co","Gabe3@m.co"],["Hanzo","Hanzo0@m.co","Hanzo1@m.co","Hanzo3@m.co"],["Kevin","Kevin0@m.co","Kevin3@m.co","Kevin5@m.co"],["Fern","Fern0@m.co","Fern1@m.co","Fern5@m.co"]]
```

**Constraints:**

- `1  0)` is a valid email.

**Patterns:** `union-find`, `merge-intervals`

## Java Solution

```java
package graph;

import java.util.*;

public class AccountsMerge {
    public List<List<String>> accountsMerge(List<List<String>> accounts) {
        Map<String, String> emailToName = new HashMap<>();
        Map<String, String> parent = new HashMap<>();

        for (List<String> account : accounts) {
            String name = account.getFirst();

            for (int i = 1; i < account.size(); i++) {
                String email = account.get(i);
                emailToName.put(email, name);
                parent.put(email, email);
            }
        }

        for (List<String> account : accounts) {
            String firstEmail = account.get(1);
            for (int i = 2; i < account.size(); i++) {
                union(parent, firstEmail, account.get(i));
            }
        }

        Map<String, TreeSet<String>> unions = new HashMap<>();
        for (String email : parent.keySet()) {
            String root = find(parent, email);
            unions.computeIfAbsent(root, x -> new TreeSet<>()).add(email);
        }

        List<List<String>> result = new ArrayList<>();
        for (String root :unions.keySet()) {
            List<String> merged = new ArrayList<>();
            merged.add(emailToName.get(root)); // Add the name
            merged.addAll(unions.get(root)); // Add the sorted emails
            result.add(merged);
        }

        return result;
    }

    private void union(Map<String, String> parent, String e1, String e2) {
        String p1 = find(parent, e1);
        String p2 = find(parent, e2);
        if (!p1.equals(p2)) {
            parent.put(p1, p2);
        }
    }

    private String find(Map<String, String> parent, String email) {
        if (!parent.get(email).equals(email)) {
            parent.put(email, find(parent, parent.get(email)));
        }
        return parent.get(email);
    }
}
```

## Explanation

### Problem Analysis
Each account gives a name followed by one or more emails, and accounts belonging to the same person may appear multiple times. The key detail is that shared email addresses, not shared names, determine whether two accounts must be merged.

This is a common interview problem because it tests whether you can model “belongs to the same group” as connected components and then rebuild the grouped result cleanly.

### Approach
The code treats every email as a node in a Union-Find structure. If two emails appear in the same account, they must belong to the same person, so they are unioned into one component.

The solution proceeds in three stages:
- map every email to its owner name and initialize each email as its own parent
- union all emails within the same account
- group emails by their final root and output each component in sorted order

This is more efficient than repeatedly merging whole account lists, because Union-Find is designed exactly for dynamic grouping.

### Pattern Used
Union-Find (Disjoint Set Union) with path compression.

### Key Insight
All emails in the same connected component belong to the same merged account, even if the connection is indirect through multiple original accounts.

### Code Walkthrough
The method `accountsMerge(List<List<String>> accounts)` starts with two maps:
- `emailToName` maps each email to the account holder's name
- `parent` stores the Union-Find parent of each email

In the first loop over `accounts`, the code reads:
- `String name = account.getFirst();`

Then for every email in that account:
- `emailToName.put(email, name);`
- `parent.put(email, email);`

So every email is registered and initially points to itself.

The second pass performs the unions. For each account:
- `String firstEmail = account.get(1);`

Then every later email in the same account is unioned with `firstEmail`:
- `union(parent, firstEmail, account.get(i));`

That makes all emails in one account part of the same set.

After all unions are done, the code builds grouped components using:
- `Map<String, TreeSet<String>> unions = new HashMap<>();`

For each `email` in `parent.keySet()`:
- `String root = find(parent, email);`
- `unions.computeIfAbsent(root, x -> new TreeSet<>()).add(email);`

This finds the representative of the component and inserts the email into a `TreeSet`, which keeps emails sorted automatically.

Finally, the result is built:
- create `merged = new ArrayList<>()`
- `merged.add(emailToName.get(root))`
- `merged.addAll(unions.get(root))`
- `result.add(merged)`

The helper `union(...)` finds the roots `p1` and `p2` and links one root to the other if they differ.

The helper `find(...)` performs path compression:
- if an email is not its own parent, recursively find the ultimate parent
- update `parent.put(email, ...)` so future lookups are faster

### Example Walkthrough
Use Example 1.

Accounts:
- `['John','johnsmith@mail.com','john_newyork@mail.com']`
- `['John','johnsmith@mail.com','john00@mail.com']`
- `['Mary','mary@mail.com']`
- `['John','johnnybravo@mail.com']`

After initialization:
- each email is its own parent
- `emailToName` maps each email to `John` or `Mary`

Union phase:
- In the first account, `john_newyork@mail.com` is unioned with `johnsmith@mail.com`
- In the second account, `john00@mail.com` is unioned with `johnsmith@mail.com`
- The third and fourth accounts have only one email, so no extra union is needed

Now these three emails are connected:
- `johnsmith@mail.com`
- `john_newyork@mail.com`
- `john00@mail.com`

Grouping phase:
- `find(...)` returns the same root for those three emails, so they go into one `TreeSet`
- `mary@mail.com` forms its own group
- `johnnybravo@mail.com` forms its own group

Because `TreeSet` sorts automatically, the merged John account becomes:
- `['John', 'john00@mail.com', 'john_newyork@mail.com', 'johnsmith@mail.com']`

That matches the expected output.

### Key Variables Explained
- `emailToName`: remembers which name should be placed at the front of each merged account.
- `parent`: Union-Find parent map for every email.
- `account`: current list being processed from `accounts`.
- `firstEmail`: anchor email used to union all emails of the same account together.
- `unions`: maps each root email to the sorted set of emails in that component.
- `result`: final list of merged accounts.
- `p1`, `p2`: roots found during `union(...)`.
- `root`: representative email returned by `find(...)` for grouping.

### Why This Works
The Union-Find invariant is that emails connected directly or indirectly by account membership end up with the same root.

- Every email starts in its own singleton set.
- Unioning each account's emails with `firstEmail` guarantees all emails from that account are in one component.
- If two accounts share an email, unions from both accounts connect them into the same larger component.
- During grouping, calling `find(...)` on every email collapses the structure to the correct representative, so each connected component is collected exactly once.

Since the problem defines shared-email accounts as belonging to the same person, grouping by connected component is exactly the correct result.

### Trick Used
Using a `TreeSet` for each component so the emails are kept sorted automatically while they are grouped.

### Edge Cases Handled
- Accounts with only one email: they remain a single-node component and are still returned correctly.
- Same name used by different people: the code merges only by shared email, never by name alone.
- Indirect merges across multiple accounts: Union-Find captures transitive connections automatically.
- Repeated `find(...)` calls on deep chains: path compression in `find(...)` flattens them for future lookups.

### Complexity Analysis
Let `E` be the total number of email entries across all accounts.

- **Time Complexity:** `O(E log E)` overall. Building the maps is `O(E)`, Union-Find operations are near-linear with path compression, and inserting emails into `TreeSet` objects adds the sorting cost that dominates the total.
- **Space Complexity:** `O(E)` because `emailToName`, `parent`, `unions`, and the output all store emails proportional to the input size.
