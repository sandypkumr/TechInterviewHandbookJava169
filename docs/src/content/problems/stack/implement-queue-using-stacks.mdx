Implement a first in first out (FIFO) queue using only two stacks. The implemented queue should support all the functions of a normal queue (`push`, `peek`, `pop`, and `empty`).

Implement the `MyQueue` class:

- `void push(int x)` Pushes element x to the back of the queue.

- `int pop()` Removes the element from the front of the queue and returns it.

- `int peek()` Returns the element at the front of the queue.

- `boolean empty()` Returns `true` if the queue is empty, `false` otherwise.

**Notes:**

- You must use **only** standard operations of a stack, which means only `push to top`, `peek/pop from top`, `size`, and `is empty` operations are valid.

- Depending on your language, the stack may not be supported natively. You may simulate a stack using a list or deque (double-ended queue) as long as you use only a stack's standard operations.

**Example 1:**

```
Input
["MyQueue", "push", "push", "peek", "pop", "empty"]
[[], [1], [2], [], [], []]
Output
[null, null, null, 1, 1, false]

Explanation
MyQueue myQueue = new MyQueue();
myQueue.push(1); // queue is: [1]
myQueue.push(2); // queue is: [1, 2] (leftmost is front of the queue)
myQueue.peek(); // return 1
myQueue.pop(); // return 1, queue is [2]
myQueue.empty(); // return false
```

**Constraints:**

- `1 amortized** `O(1)` time complexity? In other words, performing `n` operations will take overall `O(n)` time even if one of those operations may take longer.

## Java Solution

```java
package stack;

import java.util.Stack;

public class ImplementQueueUsingStacks {
    private Stack<Integer> stack1;
    private Stack<Integer> stack2;

    public ImplementQueueUsingStacks() {
        stack1 = new Stack<>();
        stack2 = new Stack<>();
    }

    public void push(int x) {
        stack1.push(x);
    }

    public int pop() {
        if (stack2.isEmpty()) {
            while (!stack1.isEmpty()) {
                stack2.push(stack1.pop());
            }
        }
        return stack2.pop();
    }

    public int peek() {
        if (stack2.isEmpty()) {
            while (!stack1.isEmpty()) {
                stack2.push(stack1.pop());
            }
        }
        return stack2.peek();
    }

    public boolean empty() {
        return stack1.isEmpty() && stack2.isEmpty();
    }
}
```

## Explanation

### Problem Analysis

This problem asks us to simulate queue behavior, which is FIFO, using only stack operations, which are naturally LIFO. The challenge is not just storing values, but making sure `push`, `pop`, `peek`, and `empty` all behave exactly like a real queue.

This is a common interview topic because it tests whether you understand how to combine simple data structures to recreate a different access pattern.

### Approach

The code uses two stacks:

- `stack1` collects newly pushed elements.
- `stack2` serves elements in queue order.

Instead of reordering elements on every `push`, the solution delays the transfer until `pop()` or `peek()` needs the front element and `stack2` is empty. That lazy transfer is what avoids the brute-force cost of moving elements back and forth on every operation.

### Pattern Used

This solution primarily relies on **stack simulation / amortized design** using two stacks.

### Key Insight

If all elements are moved from `stack1` to `stack2` only when `stack2` becomes empty, their order is reversed exactly once, which makes the oldest inserted element appear on top of `stack2`.

### Code Walkthrough

The constructor creates two empty stacks:

- `stack1 = new Stack<>();`
- `stack2 = new Stack<>();`

In `push(int x)`, the code simply does `stack1.push(x)`. That keeps insertion cheap and postpones any expensive work.

In `pop()`:

- If `stack2.isEmpty()`, the code moves everything from `stack1` into `stack2` with:
  - `while (!stack1.isEmpty()) { stack2.push(stack1.pop()); }`
- After that transfer, the front queue element is on top of `stack2`.
- `return stack2.pop();` removes and returns that front element.

In `peek()`:

- It uses the same transfer logic when `stack2` is empty.
- Instead of removing the value, it returns `stack2.peek()`.

In `empty()`:

- The queue is empty only when both stacks are empty.
- That is why the code returns `stack1.isEmpty() && stack2.isEmpty()`.

### Example Walkthrough

Using the given sequence:

- `push(1)`  
  - `stack1 = [1]`, `stack2 = []`
- `push(2)`  
  - `stack1 = [1, 2]`, `stack2 = []`
- `peek()`  
  - `stack2` is empty, so transfer from `stack1` to `stack2`
  - move `2`, then `1`
  - now `stack1 = []`, `stack2 = [2, 1]`
  - `stack2.peek()` returns `1`
- `pop()`  
  - `stack2` is not empty, so no transfer is needed
  - `stack2.pop()` returns `1`
  - queue now effectively contains only `2`
- `empty()`  
  - `stack1` is empty, but `stack2` still contains `2`
  - result is `false`

That matches the expected output.

### Key Variables Explained

- `stack1`: holds the newest elements in insertion order.
- `stack2`: holds elements in the order needed for queue removal and front access.
- `x`: the value passed into `push(int x)`.

The important state change is that elements move from `stack1` to `stack2` only when `stack2` runs out.

### Why This Works

At any moment:

- values still in `stack2` are the oldest queue elements that must be served first,
- values in `stack1` are newer elements waiting for their turn.

When `stack2` becomes empty, transferring all elements from `stack1` reverses their order. That reversal makes the oldest among them appear on top, which restores FIFO behavior. Because the code never mixes partial transfer logic, the queue order stays correct across all operations.

### Trick Used

The main trick is **lazy transfer**: move elements from `stack1` to `stack2` only when `stack2` is empty.

### Edge Cases Handled

- Multiple consecutive `push()` calls: all new values safely accumulate in `stack1`.
- Repeated `pop()` or `peek()` calls: as long as `stack2` still has items, no unnecessary transfer happens.
- Empty-state check: `empty()` correctly handles cases where one stack is empty and the other is not.

The code assumes `pop()` and `peek()` are called only when the queue is valid to read, which matches the problem contract.

### Complexity Analysis

- **Time Complexity: `O(1)` amortized per operation**  
  `push()` is always `O(1)`. A single call to `pop()` or `peek()` can trigger a transfer that takes `O(n)`, but each element is moved from `stack1` to `stack2` at most once and popped at most once overall, so across many operations the average cost is `O(1)` each.
- **Space Complexity: `O(n)`**  
  Across `stack1` and `stack2`, the queue stores at most `n` elements total.
